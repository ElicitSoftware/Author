\section{What a survey is made of}
\markboth{What a survey is made of}{}

An Elicit survey is a decision tree a respondent walks through. What they answer decides what
they see next, so designing a survey means designing that path. Everything in this manual uses
the same names and the same glyphs the application puts on screen.

\subsection{The containers}

Everything sits inside something else:

\begin{itemize}
  \item A \term{survey} holds steps.
  \item A \term{step} is a page in the respondent's progress bar. On the designer board it is a
        lane that groups related sections.
  \item A \term{section} is a titled group of questions on that page. On the board it is a card
        inside a lane.
  \item A \term{question} is one input the respondent answers. On the board it is a row inside a
        card, carrying a glyph that shows its type.
\end{itemize}

Steps run in order, sections run in order within their step, and questions run in order within
their section. Unless a rule says otherwise, that display order is exactly what the respondent
experiences.

Only the first step is built when a respondent signs in. The survey creates and saves every
element no rule controls before the first page appears, so everything after the first step is
built \emph{just in time} instead — by a Show or Repeat rule, at the moment the respondent's
answers call for it. That keeps the first page fast, and it keeps the database free of questions
nobody sees: a respondent who abandons the survey in the first step or two has had only those
steps saved. Every step, section and question after the first step therefore needs a rule that
builds it (see \emph{Connecting questions with rules}).

\subsection{The rules}

A \term{rule} reads the answer to one upstream question, compares it with a reference value using
an operator, and when the comparison holds performs an action on one downstream target — a step,
a section or a question. Every rule is the same sentence:

\begin{quote}
\ui{question} \; (\ui{operator}) \; \ui{value} \; $\rightarrow$ \; (\ui{action}) \; \ui{target}
\end{quote}

There are three actions:

\begin{itemize}
  \item \term{Show} — the target appears only when the rule holds. Until then the respondent
        never sees it.
  \item \term{Repeat} — the target section or question is repeated as many times as the answer
        says, for example one \ui{Child} section per child. When the answer is a selection from
        a list, the target is repeated once for each item selected instead, for example one
        \ui{Game} section per game attended.
  \item \term{Text} — the answer is written into the target's text wherever a
        \texttt{\{<TOKEN>|default\}} placeholder appears, so a later question can say
        ``your daughter'' rather than ``your child''.
\end{itemize}

There is no Hide rule. Hiding is the same as not showing: give the element a Show rule and it
stays hidden until that rule holds. The operators are Boolean, Greater than, Equal, Not equal,
Field exists and Contains. When several rules point at the same target, all of them must hold.

\begin{elicitnote}[The same page, inside the application]
Everything in this section is also on the \ui{How surveys work} page in the application
navigation, with the glyphs drawn live. This manual is its printable form, and adds the
step-by-step procedure that follows.
\end{elicitnote}

\subsection{Identity and publishing}

Every element gets a key the moment it is created and keeps it for life. Removing an element
\term{retires} it rather than deleting it, so answers already recorded at a site keep their
meaning. When the survey is ready you \term{export} a \texttt{.elicit} file; the Admin app
installs it at a site the first time and updates it in place after that, matching elements by
key. Deleting a whole survey is the one thing that does remove rows; it has its own section at
the end, because it cannot be undone.

\begin{elicitnote}[Vocabulary]
Author never uses ``publish'' for a state in the database — the verb is \emph{export}. The
credential a respondent enters to reach a survey is the \term{access code}, never a token;
``token'' means only the \texttt{\{<KEY>|default\}} placeholder in question text.
\end{elicitnote}

\section{Signing in}
\markboth{Signing in}{}

Author uses the platform's identity provider, the same one as the Admin and Survey apps. Open
Author in a browser and you are sent to the sign-in page.

\screenshot{01-sign-in}{The identity provider's sign-in page. Author itself never asks for a
password.}

Authoring requires the \texttt{elicit\_author} role. It is granted explicitly and is \emph{not}
implied by \texttt{elicit\_admin}: an administrator who has not been given it can open the
System pages but not a survey. If you sign in and the surveys are not there, that role is the
first thing to check with whoever administers your identity provider.

After signing in you land on the \ui{Surveys} list, the application's front door.

\screenshot{02-surveys-list}{The Surveys list. Every survey you can edit, with who last edited
it and the note from its last export.}

\section{Creating a survey}
\markboth{Creating a survey}{}

Choose \ui{New survey}. A survey needs two things to exist: a \ui{Name}, which is the machine
name and may not contain spaces, and a \ui{Title}, which is what a respondent sees.

\screenshot{03-new-survey}{Creating a survey. Name and Title are required; the rest can be filled
in later from \ui{Edit details}.}

\begin{itemize}
  \item \ui{Name} — the machine name, for example \texttt{FamilyHistory}. No spaces.
  \item \ui{Title} — the respondent-facing title, for example ``Family Health History''.
  \item \ui{Description} — a note for your colleagues; respondents never see it.
  \item \ui{Initial display key} — where the respondent starts. Leave it empty unless you have a
        reason not to.
  \item \ui{Post-survey address} — where the respondent is sent when they finish.
\end{itemize}

Save, and the survey appears in the list. Open it and you get its overview: the survey key, when
it was last exported, the four things you can do to it, and a validation panel.

\screenshot{04-survey-overview}{A survey's overview page. The validation panel is the thing to
watch — it is what stands between you and a clean export.}

The validation panel is live. It tells you what is still wrong with the definition — a survey
with no steps, a choice question with no list, a rule that points backwards — and it has to read
``Ready to export. No problems found.'' before the export is worth doing.

\section{Starting from an AI draft}
\markboth{Starting from an AI draft}{}

There is a third way to start, beside the empty form and importing a file someone sent you: have
an AI agent write the first draft. Choose \ui{Draft with AI}, beside \ui{New survey} on the
surveys list and in the navigation.

Author does none of the drafting. What the page gives you is the \emph{specification} --- one
self-contained document that teaches an agent the survey model and the exact record format of a
\texttt{.elicit} file --- and the four steps of the round trip:

\begin{enumerate}
  \item \ui{Copy prompt to clipboard} puts a short instruction and the whole specification on
        your clipboard, ready to paste into any AI session. \ui{Download the specification}
        saves the same document as a file, for an agent you would rather attach it to.
  \item Describe the survey you want. A good agent will ask you the questions that decide
        structure: the topics to cover, what repeats per person or per item, what has to be
        conditional.
  \item Save the \texttt{.elicit} file it writes.
  \item Bring it back to \ui{Import definition}. The two pages link to each other.
\end{enumerate}

\begin{elicitnote}[Nothing leaves the building on its own]
Author sends nothing to any AI service and needs no account with one. You carry the
specification out and you carry the draft back, so this works with whatever agent you already
use, and a deployment with no outbound network access loses nothing.
\end{elicitnote}

A draft is not a deployable definition. It is marked so that only Author will read it --- the
Admin console refuses it --- and it arrives here with no keys of its own: Author mints the
survey key and every element key on import, so what you get is an ordinary working copy, exactly
like one you had typed yourself.

Expect to correct things. Open the imported survey and read the validation panel: an agent that
has never seen your data will get some rules backwards and leave some lists empty. Fix them in
the designer, or hand the findings back to the agent and import a corrected draft as a second
survey. Nothing is deployed until you export it yourself.

\section{Laying out steps and sections}
\markboth{Laying out steps and sections}{}

Choose \ui{Design…} from the survey overview. The drawer on the left is your toolbox; the board
on the right is the survey; the panel beside the board previews the selection as a respondent
will see it.

\screenshot{05-designer-board}{The designer. Controls, Lists, Sections, Questions and the
structure tree on the left; the board in the middle; the respondent preview on the right.}

Work top-down: steps, then sections, then questions, then the lists, rules and analysis tags
that give them meaning.

\subsection{Adding a step}

Use \ui{Add step} at the top of the board, or drag the \ui{STEP} glyph from \ui{Controls} onto
the board. Both open the same editor.

\screenshot{06-new-step}{A new step. \ui{Dimension name} is what the analysis schema calls this
step; it defaults to the name, and changing it later is an analysis change rather than a rename.}

\begin{elicitnote}[Everything a drag can do, a menu can do too]
Every element on the board carries a \ui{$\vdots$} menu with the same actions the drag gestures
perform, so the designer is usable without a pointer.
\end{elicitnote}

\screenshot{07-step-menu}{A step's menu: edit it, add another step after it, add a section, move
it up or down, open its details page, or remove it.}

\subsection{Adding a section}

A step with no sections shows the respondent nothing. Add one from the step's menu, or drag the
\ui{SECTION} glyph into the lane.

\screenshot{08-new-section}{A new section. The name is the page heading the respondent reads.}

One click on a lane opens it to reveal its section cards; one click on a card opens it to reveal
its question rows. A double click on any of them opens its editor.

\section{Giving choice questions their options}
\markboth{Giving choice questions their options}{}

A choice question — radio, combo box, multi-select or checkbox group — needs a \term{list of
options} before it can be saved. Define the list first, from the \ui{Lists} panel in the drawer.

\screenshot{09-list-of-options}{A new list of options. The options are in the order respondents
see them; the arrows reorder them and the coded value defaults to the display text.}

A list belongs to the survey, not to one question, so several questions can offer the same
options. Drag a list's glyph onto a question to give it those options, or pick the list in the
question's own editor.

%% ------------------------------------------------------------------ 7
\section{Adding questions}
\markboth{Adding questions}{}

Add a question from a section's menu, or drag the \ui{QUESTION} glyph — set to the type you want
— into the card.

\screenshot{10-question-editor}{A text question. \ui{Short text} is what the board and the
structure tree show; \ui{Question text} is what the respondent reads.}

The fields worth knowing:

\begin{itemize}
  \item \ui{Type} — text, integer, radio, combo box, date and the rest. The editor changes with
        the type, and the preview at the bottom shows the field the respondent will get.
  \item \ui{Short text} — the label on the board and in the structure tree. Keep it short.
  \item \ui{Question text} — what the respondent reads. This is where a
        \texttt{\{<TOKEN>|default\}} placeholder goes if a Text rule is to fill it.
  \item \ui{Required} and \ui{Validation message} — whether an answer is compulsory, and what
        the respondent is told when it is missing.
  \item \ui{Sample answer} — previews what a Text rule reading this question would write
        elsewhere.
\end{itemize}

Choose a choice type and the editor asks for the list of options you defined earlier.

\screenshot{11-choice-question}{A radio question with its list of options attached. Without a
list the editor refuses to save.}

Once a section is open you can see the whole page taking shape: rows in order, each with its type
glyph, and the respondent's view of the same page beside it.

\screenshot{12-section-opened}{A section opened on the board, with the rules drawn as arrows and
the respondent preview beside it.}

\subsection{Asking the same question twice}

The \ui{Sections} and \ui{Questions} panels in the drawer list every section and every question
in the survey once, with the number of places each appears in. Drag one into another container,
or use \ui{Also add to section…}, and it is the \emph{same} element shown in a second place — a
change to its text reaches every section it is in.

\screenshot{15-question-bank}{The Questions panel. Each question appears once, with how many
sections use it; the search box narrows the panel as you type.}

\section{Connecting questions with rules}
\markboth{Connecting questions with rules}{}

Anything conditional is a rule. Start one from the upstream question — the one whose answer is
read — using \ui{Add rule…} in its menu, or by dragging a rule glyph from \ui{Controls} onto the
question and then dragging the arrowhead onto the target.

\screenshot{13-question-menu}{A question's menu. Rules, analysis tags and report marks all start here.}

The editor is the rule sentence, in the order the runtime evaluates it.

\screenshot{14-new-rule}{A Repeat rule: when \ui{Child count} is greater than 0, repeat the
section \ui{Child} that many times.}

\begin{elicitcaution}[Rules only point forwards]
The target must come after the upstream question in the survey's order. Author refuses a rule
that points backwards and says so, because the respondent would reach the target before there is
an answer to read. A count question therefore sits in the section \emph{before} the block it
repeats — a section cannot repeat itself.
\end{elicitcaution}

\begin{elicitcaution}[Every step after the first needs a rule]
Only the first step may hold elements without a rule. Every question in a later step has to be
reached by a Show or Repeat rule — one on its step, on its section in that step, or on the
question itself; a rule reaches its target and everything inside it. Text rules do not count,
because they build nothing. For a step that always follows, the usual rule is \ui{Field exists}
$\rightarrow$ \ui{Show} on the step, read from a question on an earlier step such as its
introduction: it holds as soon as that question has been presented. Validation reports a step
nothing builds as an error, and inside a step that has rules, each section or question nothing
reaches; export waits until each has its rule.
\end{elicitcaution}

\subsection{Repeating once per selected item}

When the same questions are asked about each thing a respondent picked from a list — each game
attended, each medication taken — write those questions once and repeat them. Ask the list
question as a multi-select or a checkbox group, put the questions about one item in a section of
their own in a later step, and draw a \ui{Repeat} rule from the list question to that section.

Because the question is answered by selecting items, the rule editor says under \ui{Operator}
that the target repeats once for each item selected, and starts a new rule on
\ui{FIELD\_EXIST}, which is the operator this rule wants: nothing selected then repeats nothing.
Author refuses \ui{BOOLEAN} and \ui{GREATER THAN} here, because neither is ever true for a
selection and the section would never appear.

Give the rule a \term{token} and name it in the section's own name:

\begin{quote}
\texttt{Michigan vs.\ \{<GAME>|this game\}}
\end{quote}

Each repetition is then titled with its item's display text. The token reaches every text inside
the section, so a question can name the item too:

\begin{quote}
\texttt{Did you use the restrooms at the \{<GAME>|this\} game?}
\end{quote}

The preview shows one repetition, with the first option of the list in the token's place.

Three things follow from tying each repetition to its item rather than to a count:

\begin{itemize}
  \item The repetitions appear in the order of the list, not the order the respondent selected
        them in.
  \item A respondent who goes back and changes the selection keeps what they answered about
        every item that is still selected, and gets their answers back for an item they
        unselect and select again.
  \item Rules inside the repeated section — \emph{ask who they came with when they did not come
        alone} — are drawn once, between the section's own questions, and apply in every
        repetition.
\end{itemize}

\begin{elicitnote}[Reordering a list changes the order of the pages, nothing more]
A repetition belongs to its item by the item's position in the list, so reordering the options
of a list that drives a Repeat rule, or inserting one in the middle, changes the order in which
respondents who start after the change see the repeated section. Respondents already answering
keep the list as it was when they started. Reporting is unaffected: each repeated section's
reporting row names the item it is about by the item itself, not by its position, so rows
collected before and after a reorder report the same item.
\end{elicitnote}

A Repeat rule that reads a number is unchanged: it repeats its target that many times. In both
cases the target is a section or a question, not a step.

Rules are drawn on the board as arrows from the question that is read to the element that is
acted on, labeled with the action. Untick \ui{Show rules} at the top of the board to hide them
while you work on structure.

\section{Tagging for analysis}
\markboth{Tagging for analysis}{}

An \term{analysis tag} names a column of the star schema a site builds from the answers for
analysis. Tag a question and its answers fill that column; tag a section as it appears in a step
with a fixed value, and every respondent who reaches it is classified by that value. Tags that
share a \term{dimension} share one table of values. Tags are not reports: what a respondent or an
administrator reads is decided on the \ui{Reports…} page (next section).

Open the survey's \ui{Analysis…} page to see every tag, every assignment, and the schema they
will produce.

\screenshot{16-reporting}{The analysis page: the tags, where they are assigned, and the
dimension tables and columns the site's analysis build will create.}

Define a tag with \ui{New tag…} and attach it with \ui{Assign tag…}, or use \ui{Analysis tags…}
in a question's or section's own menu.

\screenshot{17-assign-tag}{Assigning a tag. A question can record the respondent's answer; a
section in a step can classify everyone who reaches it by a fixed value.}

\begin{elicitcaution}[Tag changes are retroactive]
Changing or removing an assigned tag relabels answers that deployed sites have \emph{already}
recorded, once the survey is exported and applied. Historical data changes with it. Treat a
tag change as a decision about past data, not only about future data.
\end{elicitcaution}

\section{Reports}
\markboth{Reports}{}

A survey can show its respondents one or more \term{reports} after they finish, and every new
survey starts with the built-in \term{respondent report}, which echoes back the answers the
author chose. The \ui{Reports…} page lists the survey's report services in the order a
respondent sees them: the built-in report is badged, and a service a site runs for this survey
is added with \ui{Add report service…}, giving its name, a description and its address. Drag a
row to reorder, \ui{Edit…} it, or \ui{Remove} it; a survey whose list is empty ends on its
post-survey address with no report page.

\begin{elicitnote}[The address is the site's]
A report service is a small web application the site runs; the platform's installation manual
describes what it is sent and what it must answer, in its custom reports chapters. The address
you give is the one the site's Survey and Admin reach it at, so agree it with whoever runs the
site, and export again when it changes: every apply replaces the site's list of report services
with the one in the file. The name and description are what the respondent reads, and are
translated with the rest of the survey.
\end{elicitnote}

What the respondent report shows, and what the administrator report monitors, are the survey's
\term{report marks}. Mark a question, a question as placed in one section, or a whole section
with \ui{Report marks…} in its menu on the board, or with \ui{Mark element…} on the
\ui{Reports…} page, choosing the report and, if the element's own text is not what the report
should say, a label. The \ui{Respondent} and \ui{Administrator} tabs list each report's marks
in order; drag to reorder, \ui{Edit label…} to change the label, \ui{Unmark} to remove.
Questions that show HTML or take a password cannot be marked.

\begin{elicitcaution}[The respondent report is as private as the access code]
A respondent reaches their report again by signing in with their access code. Marking a
sensitive question for the respondent report therefore shows its answer to anyone holding
that code.
\end{elicitcaution}

\section{Post-survey actions}
\markboth{Post-survey actions}{}

A \term{post-survey action} is something the site does at the moment a respondent finishes:
filing their results in a records system, telling a study coordinator. Each action is an
address the site's Survey calls, with the respondent's id; respondents never see it. List a
survey's actions on its \ui{Post-survey actions…} page, reached from the survey overview.

\ui{Add action…} asks for a name, a description and the address. The address must be a full
\texttt{http} or \texttt{https} address the site's Survey can reach, such as
\texttt{http://fhhs:8080/familyhistory/generate}; unlike a report service, an action has no
path form. Survey calls the actions in the order listed, each on its own, so one failing does
not stop the next; drag a row to change the order. \ui{Edit…} changes an action in place, and a
site applying the next export updates it.

Names and descriptions are notes for authors and for whoever runs the site, so they are not
translated. A new survey starts with no actions.

\begin{elicitcaution}[Removing an action removes it at the site]
A site applying the next export stops calling a removed action and deletes its record of
which respondents the action was called for. The preview Survey calls actions too: a preview
respondent who finishes triggers every action whose address the authoring stack can reach.
\end{elicitcaution}

\section{Checking and exporting}
\markboth{Checking and exporting}{}

Go back to the survey overview and read the validation panel. It must say ``Ready to export. No
problems found.'' Anything else names the element, the problem and what to do about it — fix it on
the board and the panel updates.

Then choose \ui{Export…}.

\screenshot{18-export}{Exporting. The release note is required: it is recorded on the survey and
inside the file, and it is what a colleague sees in the Surveys list.}

The export writes a \texttt{.elicit} file in the \texttt{ELICIT\_SURVEY\_EXPORT\_V1} format,
records who exported it and the note, and mints a revision. Hand that file to the Admin app's
\ui{Apply Survey Definition}: the first time it installs the survey at a site, and every time
after that it updates it in place, matching elements by their keys. Elements you removed travel
as retirements, so answers already recorded keep their meaning.

\begin{elicitnote}[The round trip]
\ui{Import definition} in the application navigation reads a \texttt{.elicit} file back into
Author for further editing, keeping every key. That is how you pick up a survey someone else
exported, or start from one of the sample definitions.
\end{elicitnote}

%% ------------------------------------------------------------------ 11
\section{Deleting a survey}
\markboth{Deleting a survey}{}

A survey you no longer need, or one you are about to replace from a file, can be deleted from the
\ui{Surveys} list: choose \ui{Delete} on its row. Unlike removing an element, which retires it,
this deletes the survey and everything in it --- steps, sections, questions, choice lists, rules,
analysis tags, reports, report marks and translations, removed elements included. Nothing in Author can bring it back.

The confirmation therefore asks for three things:

\begin{itemize}
  \item \textbf{Take the backup.} \ui{Download backup} saves the whole survey exactly as it stands
        --- even with validation errors --- to a \texttt{.elicit} file. \ui{Import definition} reads
        it back with every key unchanged, which is the only way to undo a delete.
  \item \textbf{Read what it says about sites.} If the survey has been exported, the confirmation
        names who exported it last and the release note. Author holds the master copy; every site
        that applied an export keeps its own and is not touched by the delete.
  \item \textbf{Type the survey's name.} \ui{Delete survey} stays disabled until the name matches
        exactly.
\end{itemize}

\begin{elicitnote}[Changing a site after a delete]
A site matches every update by the keys in the file. To change a site's copy later, import the
backup, edit it and export again. A survey rebuilt from scratch has new keys and would install at
the site beside the old one rather than update it.
\end{elicitnote}

The backup is not an export: it records no release note, and it is marked as a draft
(\texttt{ELICIT\_SURVEY\_DRAFT\_V1}), so the Admin app refuses it and no site can install it
by mistake. Re-import it, check the validation panel, and export as usual before it goes
anywhere.

If the survey has been walked through as a respondent in the authoring stack's preview Survey
application, the answers entered there are in Author's own database. The confirmation says how many
preview respondents the survey has, and they and their answers are deleted with it. Answers
collected at a site are never affected.
